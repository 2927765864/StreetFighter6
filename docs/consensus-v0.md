## 1. 最终要做什么

### 1.1 一句话（✅）

在 **桌面 Chrome + WebGPU** 上，用 **Three.js** 做一款 **帧数据驱动、训练场载体** 的原型：  
**目标是复刻《街霸 6》中的隆（Ryu）**（含其作为 SF6 隆所必需的共享系统），  
**对战逻辑在 2D 平面上成立，3D 负责表现与镜头。**

### 1.2 产品性质（✅）

| 是 | 不是 |
|----|------|
| 学习 / 研究向的**自用、不公开**原型 | 商业产品、公开同人发售作、正版客户端替代品 |
| **以 SF6 隆为目标**的角色复刻（可占位推进） | 原创角色、全角色表、全模式客户端 |
| **单机训练场**为主要使用形态 | 以联网对战 / 回滚同步为第一目标 |
| **Classic 操作** | Modern 操作 |
| 中文文档的私人工程 | 冒充官方或已获授权的演示 |

**主要用户（✅）**：作者本人——在训练场中推进隆的复刻、调试帧数据与系统。  
**次要（可选）**：无公开前提下，技术向自用演示。

**命名与文案（✅）**：项目**不公开**；运行时与文档**不要求中性名**，可按官方习惯使用角色名、招式位记等（如 Ryu、5LP）。架构上保持资源可替换（见 §4），**不是**为公开分发做的中性化产品要求。

### 1.3 产品由哪些部分构成（✅）

1. **可玩对战核心**  
   输入 → 状态机 → 攻击/帧数据表 → 碰撞判定 → 硬直与 cancel 等；以及使隆成为 **SF6 隆**所必需的共享系统（**Drive 等**，见 §3）。  
2. **训练场工具**  
   Dummy 对手 + 调试/帧向信息展示（边界见 §3.3）。  
3. **3D 表现**  
   角色、场景、动画、相机等，**挂在同一套 2D 对战逻辑之上**，不反过来驱动规则。  
4. **对战/角色系统 HUD**  
   血量、Drive 条等，属**对战与角色表现**，与训练调试工具分层（见 §3.3）。

### 1.4 成功时的目标画像（✅）

- 能在桌面 Chrome（WebGPU）中于**训练场**内操作隆、对抗 Dummy。  
- 规则与数值来自**本地自持数据表**（运行时权威）；内容上尽可能接近理想中的 SF6 隆。  
- 存在面向「SF6 隆」的目标清单（招式 + 必要系统）：每项为 **占位（未复刻）** 或 **已审查并人工标记（已复刻）**；禁止错规则却标成已复刻。  
- **5LP** 是第一条按完整标准打通的**样板**，证明「采信 → 本地表 → 逻辑 → 表现」管线；**不是**「整个项目只做一招」。  
- 画面可为 3D 角色与训练场景；逻辑与表现分离，无最终动画时仍可用占位推进规则。

更细的清单条目与实现顺序属于实现计划或内容清单，不在此展开。

## 2. 最终不做什么

下列内容**不是**本项目共识中的目标（除非将来明文改共识）：

| 类别 | 排除项 |
|------|--------|
| 模式与范围 | 联网对战、完整选人、故事模式、**全角色**、做成完整官方客户端 |
| 操作 | **Modern** 控制 |
| 训练工具上限之外 | Dummy **录制回放**、运行时**框/帧表编辑器**等（见 §3.3；H2 为调试工具上限） |
| 工程能力炫耀向 | 回滚净代码联网、完整回放系统 |
| 资源与法务 | 将官方或 rip 的模型/贴图/动画/音效/UI/字体等**再分发**到公开仓库或演示站 |
| 表述 | 以「官方授权 / 正版替代品」自我定位 |

**明确纳入目标、不得再当作「整段排除」的（✅）**：  
使隆成为 SF6 隆所**必需**的共享系统（**Drive 等**）。实现可占位，完成靠审查标记。  
细则级清单（DI / DR / OD / 投技 / Parry 等逐条）可另文维护目标清单，原则以「SF6 隆所必需」为准。

## 3. 复刻到什么程度（保真度共识）

### 3.1 「接近理想 SF6 隆」指什么（✅）

- **目标对象**：街霸 6 的**隆**，不是原创角色。  
- **标准含义**：尽可能接近理想中的 SF6 隆的行为与数据；**不**绑定「只能使用官方公开发布的信息」。官方不可能公开一切；**社区较权威帧站等一切有助于逼近理想隆的来源均可使用**，否则无法开展工作。  
- **操作体系**：**仅 Classic**。

### 3.2 分维度目标（✅）

| 维度 | 共识中的目标程度 |
|------|------------------|
| **角色内容** | **完整复刻 SF6 隆**（招式面 + 所需共享系统）；一次做不完则**占位**，不以「缩成几招」为成功定义 |
| **共享系统** | **包含** Drive 等隆成为 SF6 隆所必需的系统；可占位；完成靠审查标记 |
| **帧与规则数据** | 高要求：以逼近理想隆为准；**采信优先社区较权威帧站**；运行时用本地表；**已复刻**仅在审查+人工标记后 |
| **样板招** | **5LP**：第一条按完整标准打通的样板，非唯一目标 |
| **训练场 Dummy** | **D2**：站立 / 蹲防 / 站防等**预设切换**；受击后按规则硬直（非录制 AI） |
| **训练调试工具** | **H2**：状态、逻辑帧、hurt/hit 框、本招帧进度或简易帧条、cancel 窗口类提示；**不做**录制、框编辑器 |
| **系统/角色 HUD** | 血量、Drive 条等属对战表现，**不视为突破 H2** |
| **外观 / 招式动画** | 私人研究下终局**尽可能原版观感与原版动作**（自解包策略见 §5）；规则不绑死动画文件 |
| **音效** | 低要求：静音或免版权占位即可 |
| **镜头 / 特效** | 非「没有就不算复刻」的核心条件 |

### 3.3 训练场工具边界（✅）

| 层级 | 共识 |
|------|------|
| **Dummy = D2** | 站立、蹲防、站防等预设；按规则进入受击/防御硬直；**不要求** Dummy 会使用 Drive 套路或录制回放 |
| **调试 HUD = H2** | 框体、帧与状态、简易帧条/cancel 提示等；上限不含录制与框编辑器 |
| **系统 HUD** | 血量、Drive 条等 = 角色/对战表现，与 H2 分列 |

### 3.4 数据权威：三层关系（✅）

| 层 | 含义 |
|----|------|
| **内容采信** | **优先社区较权威帧站**（最便于逼近理想隆；相信群体整理）。官方公开资料、游戏内对照、解包等可作补充。站际冲突时，以审查后写入本地的结论为准。 |
| **运行时** | 逻辑**只读本地自持帧表/角色数据**；不直接请求社区站。 |
| **质量状态** | 仅 **审查完成且人为标记** 的条目算 **已复刻**。标记粒度：**按招** + **按系统块**。 |

**运行时与改表（R2）（✅）**：

- 判定、硬直、cancel 等由**帧表驱动**，不由动画 clip 长度驱动规则。  
- 发现与理想隆不符时，允许作为**内容决策**修改本地表（或映射），再让动画去贴合；不是「动画永远优先」。

### 3.5 占位与「已复刻」（✅）

| 允许 | 禁止 |
|------|------|
| **数据占位**：帧数/伤害等先按社区公开数据或近似写入；动画可用通用 punch / 冻帧 / 空 | 使用**错误规则**「先随便打着玩」却标成**已复刻** |
| **行为占位**：招能出、有硬直；数值先抄公开数据再校准 | 无审查标记却宣称整角色已完成 |

**已复刻** = 审查完成 **并且** 人为标记。未标记即未复刻（即使可玩占位）。

### 3.6 与「仅一招实验」的关系（✅）

历史表述中的「严格对齐一招」收束为：  
**5LP 是完整标准下的第一条样板**，用于验证采信→本地表→逻辑→表现；项目目标仍是 **完整 SF6 隆（可占位）**。

## 4. 怎么做到（原则与技术路径）

### 4.1 总原则（✅）

1. **逻辑在 2D，表现可 3D**  
   逻辑侧视轴；渲染映射到 3D。  
2. **数据驱动 + R2**  
   攻击与硬直等来自本地表；动画是皮肤；为贴理想隆可改表。  
3. **逻辑与渲染分离**  
   `帧数据 / 状态机 / 碰撞` 不依赖 GPU；Three.js + WebGPU 负责显示与调试绘制。  
4. **表现可替换（P2）**  
   稳定逻辑 id / `clipId` 映射；换临时皮或原版皮不推翻规则层。项目不公开，但架构保持可换皮。  
5. **占位推进、审查升格**  
   缺的内容用合法占位；只有标记后才算已复刻。  
6. **私人研究**  
   原版向提取物仅本机私有路径；**不**再分发；项目共识为**不公开**。

### 4.2 技术选型（✅ 高层）

| 层 | 共识 |
|----|------|
| 语言 | TypeScript |
| 渲染 | Three.js + **WebGPURenderer**（**硬要求**；不承诺 WebGL 回退） |
| 运行环境 | **桌面 Chrome** 优先 |
| 对战逻辑 | 与 Three **解耦** 的纯 TypeScript 模块 |
| 空间 | 逻辑 `(x, y)` 侧视；渲染映射到 3D 场景 |
| 输入 | 键盘为默认方案；手柄可扩展；**Classic 输入语义** |
| 构建 | SPA（如 Vite） |
| 测试侧重 | 逻辑层可单测优先于截图比对 |

### 4.3 需要掌握 / 用到的技术能力（✅ 类别）

| 类别 | 内容 |
|------|------|
| 格斗逻辑 | 固定逻辑帧、输入、状态机、框体、硬直/cancel、以及 Drive 等共享系统；**角色控制设计共识** → `docs/character-control/consensus-design-v0.md`；动作表 → `docs/character-control/action-tables/` |
| 数据与内容管线 | 本地帧表/角色数据、来源标注、占位与**已复刻**标记、clip 映射 |
| 实时渲染 | WebGPU 下 Three 场景、glTF、蒙皮动画、调试叠加层、系统 HUD |
| 资源工程（表现终局） | 正版客户端自解包 → DCC → glTF 等 |
| 资源工程（表现占位） | 许可清晰的第三方模型/通用动作 |
| 明确不依赖（当前目标） | 联网回滚、WASM/定点数（除非将来改共识） |

### 4.4 架构参考（✅ 用法）

可学习开源格斗框架与 Web 3D 案例的结构，不复制 SF6 受保护资产。  
细节 → `docs/research/community-assets-and-cases.md` 等。

### 4.5 留给 ADR 的细化（非目标歧义）（✅ 归类）

下列**不改变「最终是什么」**，实现前用 ADR 定即可，**不作为目标层未决**：

- 逻辑帧率、世界单位与模型缩放  
- 帧数据 schema 字段级定义  
- 源码目录与模块边界命名

## 5. 需要什么（素材、来源与约束）

### 5.1 需要哪些类素材（✅）

| 用途 | 需要什么 | 角色 |
|------|----------|------|
| 规则与数值 | 本地帧表 / 角色与系统数据（含占位与已复刻标记） | **运行时权威** |
| 帧数据来源 | 社区较权威帧站等（写入本地前的采信输入） | **内容采信优先** |
| 角色外形 | 模型（几何、蒙皮、贴图） | 表现；终局偏原版 |
| 动作 | 移动、攻击、受击、系统相关动画等 | 表现；服从/贴合帧表 |
| 场景 | 训练场或等价空间 | 表现 |
| 调试占位 | 通用 humanoid / 几何体 | 管线验证 |
| UI / 音效 | 训练调试层 + 系统 HUD；音效可选 | 不用官方包再分发 |

### 5.2 来源策略（✅）

| 策略 | 共识 |
|------|------|
| **帧 / 规则** | **优先社区较权威帧站** → 整理进本地表 → 审查标记后升格为已复刻；不闭门自测优先于社区 |
| **表现终局（模型/原版动作）** | **本人正版** → **自行解包** → 运行时格式；**不以**网盘 rip 为动作权威 |
| **表现占位** | 许可清晰的社区/CC0 模型与通用动作，可替换 |
| **仓库** | 提取物与大型私有资源在 `private/`（或等价）；**永不**提交公开 git |
| **环境** | 解包侧重 Windows 原生 + 正版客户端；Web 开发可在 Mac；→ `docs/guides/scheme-c-asset-pipeline.md` |

### 5.3 法律与分发红线（✅）

**不得**再分发到公开仓库或公开演示站：官方/rip 的模型、贴图、动画、音效、BGM、字体、UI、立绘等，以及伪正版包装物。

**可接受（私人研究）**：游玩与录像自学；使用社区帧站整理*自己的*本地表；截图留个人笔记。

**公开性（✅）**：本项目共识为**不公开**。不因此取消「禁止再分发提取物」的红线。架构保持可换皮，以备将来若改变公开策略时不必推翻逻辑层；**当前产品不要求中性命名与原创皮作为默认运行形态**。

### 5.4 逻辑与素材（✅）

- 无原版动画时，仍可用本地帧表 + 占位推进规则。  
- 有动画时服务观感；与表冲突时按 **R2** 处理（改表或改映射贴合理想隆，而非 clip 劫持规则）。  
- 社区临时模型 ≠ 放弃自解包终局；≠ 承认盗版资源包为权威。
